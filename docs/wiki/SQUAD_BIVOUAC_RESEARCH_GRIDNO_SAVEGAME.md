# SQUAD_BIVOUAC — Исследование: GridNo при выгрузке и целостность сейв-блока

_Техническое исследование по фиче «Бивуак отряда». Дата: 06.11.2026. Версия фичи: 2.3+ (после доработок, описанных в SQUAD_BIVOUAC_TECH.md)._

_Предмет исследования (2 вопроса):_

1. _Опасность `GridNo = -1` / непроходимых тайлов при выгрузке бивуака (`DumpToFloor`) — предметы могут «утонуть» или оказаться в стене, игрок не сможет их подобрать._
2. _Пропуск сейв-блока бивуака при несовпадении `uiVersionMarker` — корректно ли смещается указатель чтения `HWFILE`, или последующие данные сейва читаются со смещением (crash / порча сохранения)._

## Исследование 1: GridNo при выгрузке

### Загруженный сектор — цепочка AddItemToPool

**`RandomGridNo()`** (`TileEngine\Isometric Utils.cpp:1460`):

```cpp
INT32 RandomGridNo()
{
    do {
        iMapXPos = Random( WORLD_COLS );
        iMapYPos = Random( WORLD_ROWS );
        iMapIndex = iMapYPos * WORLD_COLS + iMapXPos;
    } while( !GridNoOnVisibleWorldTile( iMapIndex ) );
    return iMapIndex;
}
```

Проверяется **только видимость тайла на мировой сетке** — проходимость не проверяется вообще. Вода, тайл внутри здания, крыша — все валидны для этой функции.

**`AddItemToPool()` → `InternalAddItemToPool()`** (`Tactical\Handle Items.cpp:2932+`) — что происходит с предметом на «плохом» тайле:

| Тайл | Поведение | Последствие |
|---|---|---|
| `-1` (NOWHERE) | beta-warning + замена на `gMapInformation.sCenterGridNo` | ок, но спамит warnings |
| **Глубокая вода** | если `Item[usItem].sinks` установлен (per-item XML флаг) — **предмет не добавляется** (`return NULL`) | **безвозвратная потеря предмета** |
| **Вода** (мелкая) | предмет добавляется; `TERRAIN_IS_WATER` + `ubLevel > 0` → тайл трактуется как FLAT_GROUND | визуально на воде, подбор возможен с берега |
| **Тайл внутри стены/структуры** | предмет добавляется в item pool тайла | пул существует, но тайл непроходим — **подбор невозможен в тактике** |
| **Крыша** (`ubLevel > 0`) | если нет `FlatRoofAboveGridNo` — уровень сбрасывается на 0 | ок |

`sinks` — флаг в XML предметов (`Tactical\Item Types.h:1006`); у большинства лута (оружие, броня) он **не установлен**, но установлен у части предметов — для них вода = потеря.

**Vanilla-поведение**: `HandleLeavingOfEquipmentInCurrentSector()` (`Strategic\Map Screen Interface.cpp:1626`) — выгрузка снаряжения уволенного наёмника — использует ту же схему (`RandomGridNo()` при отсутствующем gridno). Т.е. дефект «случайный тайл без проверки проходимости» — **ванильный**, не специфичный для бивуака.

### Незагруженный сектор — entry-point и FIND_SWEETSPOT

При дампе в незагруженный сектор данных карты нет — резолв позиции возможен **только на момент загрузки сектора** (`LoadWorldItemsFromTempItemFile`, `Tactical\Tactical Save.cpp:1738+`). Два механизма:

**1. `WORLD_ITEM_GRIDNO_NOT_SET_USE_ENTRY_POINT`** (используется бивуаком):

```cpp
// Tactical Save.cpp:1752
if( pWorldItems[cnt].usFlags & WORLD_ITEM_GRIDNO_NOT_SET_USE_ENTRY_POINT )
{
    pWorldItems[cnt].sGridNo = gMapInformation.sCenterGridNo;
    pWorldItems[cnt].bRenderZHeightAboveLevel = -1;
}
```

Резолв в **центр карты без какой-либо проверки**:
- `sCenterGridNo` может быть `-1` на битых картах (worlddef.cpp:2322 считает это ошибкой карты);
- центр может оказаться водой/внутри здания — тогда предметы попадают в item pool непроходимого тайла.

**2. `WOLRD_ITEM_FIND_SWEETSPOT_FROM_GRIDNO`** (используется ванильным `AddDeadSoldierToUnLoadedSector`):

```cpp
// Tactical Save.cpp:1738
if( pWorldItems[cnt].usFlags & WOLRD_ITEM_FIND_SWEETSPOT_FROM_GRIDNO )
{
    sNewGridNo = FindNearestAvailableGridNoForItem( pWorldItems[cnt].sGridNo, 5 );
    if(TileIsOutOfBounds(sNewGridNo))
        sNewGridNo = FindNearestAvailableGridNoForItem( pWorldItems[cnt].sGridNo, 15 );
    ...
}
```

Ищет ближайший **достижимый пешком** тайл через pathing от «sweet spot». Именно поэтому в DumpToFloor нельзя использовать этот флаг с `gridno = -1`: `FindNearestAvailableGridNoForItem(-1, ...)` строит путь от невалидной точки (dummy soldier получает `sGridNo = -1`, `FindBestPath` от -1 не работает) — предметы остаются с `sGridNo = -1` и попадают в fallback `AddItemToPool(-1 → center)` с beta-warning. Это задокументировано в инварианте DumpToFloor («не FIND_SWEETSPOT — pathing от -1 теряет предметы»).

**`FindNearestAvailableGridNoForItem(sSweetGridNo, ubRadius)`** (`Tactical\Handle Items.cpp:6758`) — ключевая функция безопасного размещения:
- создаёт dummy-солдата в точке `sSweetGridNo`;
- `FindBestPath(..., COPYREACHABLE)` помечает все тайлы в радиусе `ubRadius`, достижимые пешком из точки;
- возвращает ближайший достижимый тайл (или NOWHERE, если таких нет).

Требует **загруженной карты** (pathing по `gpWorldLevelData`), поэтому применим только в загруженном секторе или на этапе загрузки сектора из temp-файла.

### Выводы по GridNo

1. **Загруженный сектор**: риск подтверждён. `RandomGridNo()` + `AddItemToPool` могут утопить (`sinks`) или замуровать предметы. Дефект ванильный (есть в `HandleLeavingOfEquipmentInCurrentSector`), но для бивуака — где выгружается ценный накопленный лут — критичнее.
2. **Незагруженный сектор**: механизм entry-point корректен по архитектуре (резолв при загрузке), но резолвится в `sCenterGridNo` без проверки проходимости. Использовать FIND_SWEETSPOT с `-1` нельзя. Решение — привязка к реальной позиции отряда (боец стоял в конкретной точке) + sweet-spot-резолв на загрузке.
3. Правильный якорь для дампа — **позиция уходящего/последнего бойца**, а не случайная точка или центр карты: игрок ожидает вещи там, где стоял отряд.

### Реализованные исправления

**1. Snap к проходимому тайлу в загруженном секторе** (`SquadBivouacManager::DumpToFloor` + lambda `BivouacAppendToSectorInventory`):

```cpp
if ( TileIsOutOfBounds( sDropGridNo ) )
{
    sDropGridNo = RandomGridNo();
}

// snap к ближайшему достижимому пешком тайлу
INT32 sSafeGridNo = FindNearestAvailableGridNoForItem( sDropGridNo, 10 );
if ( !TileIsOutOfBounds( sSafeGridNo ) )
{
    sDropGridNo = sSafeGridNo;
}
```

- радиус 10 тайлов покрывает практически любой случай;
- если snap не удался (изолированная точка) — сохраняется прежнее поведение (fallback `AddItemToPool`);
- снимает обе проблемы: предмет не утонет в воде и не замуруется в стене.

**2. Якорь на позицию уходящего бойца** (`AutoDumpBivouacOnSquadLoss(iSquadID, pLeavingSoldier)` — новый параметр):

```cpp
// SquadBivouacManager.cpp
INT32 sAnchorGridNo = -1;
if ( pLeavingSoldier != NULL &&
     pLeavingSoldier->sSectorX == sX && pLeavingSoldier->sSectorY == sY && pLeavingSoldier->bSectorZ == bZ &&
     !TileIsOutOfBounds( pLeavingSoldier->sGridNo ) )
{
    sAnchorGridNo = pLeavingSoldier->sGridNo;
}

DumpToFloor( iSquadID, sX, sY, bZ, sAnchorGridNo );
```

- вызовы в `StrategicRemoveMerc()` и `StrategicHandlePlayerTeamMercDeath()` передают уходящего/погибшего бойца;
- **загруженный сектор**: дамп на позиции бойца (со snap'ом из п.1);
- **незагруженный сектор**: gridno бойца записывается в temp-файл как обычный gridno (без entry-point флага), при загрузке сектора предмет кладётся в эту точку; passability-фикс на загрузке обеспечивается механизмом `AddItemToPool` (fallback на center при NOWHERE) — а точка бойца по определению была проходимой, когда отряд стоял в секторе;
- для дампа через кнопку «Выгрузить всё» (без уходящего бойца) сохраняется прежнее поведение: `RandomGridNo()` + snap / entry-point.

**Не изменено (осознанно)**:
- ванильные пути (`HandleLeavingOfEquipmentInCurrentSector`, `AddDeadSoldierToUnLoadedSector`) — вне scope фичи;
- механизм entry-point для случая «нет якоря» — альтернативы без данных карты нет.

## Исследование 2: uiVersionMarker и пропуск сейв-блока

### Как устроен блок бивуака в сейве

Блок вставлен в `SaveSquadInfoToSavedGameFile` / `LoadSquadInfoFromSavedGameFile` (`Tactical\Squads.cpp`) сразу после `SquadMovementGroups` — позиция зафиксирована:

```cpp
// Squads.cpp:1343
if( guiCurrentSaveGameVersion >= SQUAD_BIVOUAC_SAVEGAME )
{
    if( !SQBM().Load( hFile ) )
    {
        return( FALSE );
    }
}
```

Формат блока (v1, до исправления):

```
[UINT32 marker = 1] [UINT32 numSquads] { [UINT32 slotCount=30] [30 × OBJECTTYPE::Save()] } × numSquads
```

`OBJECTTYPE::Save()` — **самоописывающий, переменной длины**: `SIZEOF_OBJECTTYPE_POD + int size + size × (вложенный OBJECTTYPE + LBE-узлы при наличии)`. Следствие: **по маркеру нельзя вычислить длину блока** — чтобы «перепрыгнуть» блок, нужно либо читать его целиком (распаковывая структуру), либо знать размер заранее.

### Поведение при несовпадении маркера (до исправления)

Цепочка при `marker != 1`:

1. `SquadBivouacManager::Load()` возвращал `FALSE`;
2. `LoadSquadInfoFromSavedGameFile()` → `return FALSE`;
3. `LoadSavedGame()` (`SaveLoadGame.cpp:4718`): `FileClose(hFile); return FALSE` — **вся загрузка сейва прерывается**, игрок видит отказ загрузки.

**Уточнение к исходной гипотезе**: рассинхронизации чтения и порчи сейва **не происходило** — load прерывался целиком, файл не повреждался. Заявление документации «блок пропускается» было неточным (пропуск выполняется только для старых сейвов по версии, см. ниже). Реальная проблема — **жёсткий отказ загрузки** сейва, написанного будущей версией игры (например, сейв из билда с форматом v3 не открылся бы в билде с v2, хотя игра могла бы загрузить его без бивуаков).

### Поведение старых сейвов (<152)

Корректно: блок отсутствует, чтение обёрнуто в проверку версии — указатель не смещается, последующие блоки (`StrategicMovementGroups` и далее) читаются с правильных позиций. Проблемы нет.

### Выводы по маркеру

1. Старые сейвы (<152) — обрабатываются корректно (пропуск по версии сейва, не по маркеру блока).
2. Несовпадение маркера внутри блока не рассинхронизировало файл, но полностью убивало загрузку сейва.
3. Для forward-compatibility (сейв из более нового билда должен хотя бы загружаться) нужен **размер блока в заголовке** — тогда неизвестный формат можно `FileSeek`-нуть, это стандартный паттерн проекта (`strategicmap.cpp:5353` — seek по размеру; `STCI.cpp:212` — пропуск секций).

### Реализованные исправления — формат v2

Формат блока поднят до **v2** с полем размера:

```
v1 (savegame 152, без size):  [marker=1][numSquads]{...}          — legacy, читать нельзя при чужом маркере
v2 (текущий):                 [marker=2][blockSize][данные...]    — blockSize = байт после поля size
```

**Save** (`SquadBivouacManager::Save`):

```cpp
// 1. пишем marker
// 2. запоминаем позицию, пишем placeholder UINT32 для blockSize
// 3. пишем данные блока (numSquads + squads)
// 4. sBlockEndPos = FileGetPos()
// 5. FileSeek(sBlockSizePos, FROM_START) -> FileWrite(blockSize = sBlockEndPos - sBlockStartPos)
// 6. FileSeek(sBlockEndPos, FROM_START)  — вернуть позицию потока в конец блока
```

**Load** (`SquadBivouacManager::Load`):

| Ситуация | Поверхностное поведение | Поведение |
|---|---|---|
| `marker == 2` (текущий) | обычная загрузка (size читается для единообразия структуры) | |
| `marker == 1` (savegame 152 dev-ветки) | **полная загрузка без бивуаков** | |
| `marker > 2` (будущий формат) | читает `blockSize`, sanity-проверка (0 или >64MB → отказ), `FileSeek(blockSize, FROM_CURRENT)` → **сейв загружается, бивуаки пустые**, последующие блоки читаются с корректной позиции | |
| мусор в маркере/size | sanity-проверка отсекает, отказ загрузки — аккуратный, без рассинхрона | |

_Исправление 06.11.2026: изначально `marker == 1` давал отказ загрузки, из-за чего существующие сейвы, созданные exe до перехода на v2, переставали загружаться (ошибка «при загрузке игры»). v1 — известный формат (отличается только отсутствием size-поля), поэтому он читается полностью._

**Инвариант сохранён**: перед любым исходом `Load()` бивуаки сначала обнуляются — частично прочитанные данные не могут остаться в менеджере.

**Совместимость**:
- сейвы 152 (v1) от предыдущей dev-версии: **загружаются полностью** (v1 — известный формат без size-поля, читается как есть; см. исправление 06.11.2026 выше);
- сейвы <152: как раньше, пустые бивуаки;
- сейвы v2+ из будущих билдов: загрузка с пустыми бивуаками вместо полного отказа.

## Чек-лист тестирования

### GridNo при выгрузке

- [ ] Загруженный сектор, дамп через кнопку «Выгрузить всё» без якоря: вещи на земле в проходимой точке (не в воде/стене)
- [ ] Загруженный сектор, авто-дамп при увольнении последнего бойца: вещи на тайле бойца или рядом (радиус ≤10)
- [ ] Сектор с водой: предмет с `sinks=1` не тонет (snap уводит точку с воды)
- [ ] Сектор с плотной застройкой: предметы не оказываются внутри стен
- [ ] Незагруженный сектор, авто-дамп (контракт истёк у отряда в мирном секторе): вещи в temp-файле, при загрузке сектора — в точке бойца
- [ ] Незагруженный сектор, дамп через кнопку: вещи через entry-point (центр карты), как раньше
- [ ] Секторный инвентарь открыт при дампе: вещи в снапшоте на проходимой точке
- [ ] Островной случай (snap не нашёл достижимый тайл в радиусе 10): прежнее поведение, без краша

### Сейв-блок

- [ ] Новый сейв (v2): сохранение и загрузка, бивуаки восстановлены, позиция потока после блока корректна (все последующие системы загружены)
- [ ] Сейв v1 (152 от dev-ветки): **загружается полностью** (исправлено 06.11.2026), бивуаки восстановлены
- [ ] Старый сейв <152: загрузка, бивуаки пусты, без краша
- [ ] Имитация будущего формата: патч маркера на 3 в hex-редакторе → сейв загружается, бивуаки пусты, последующие системы (квесты, статистика) целы
- [ ] Имитация битого size (64MB+) в v2-блоке → отказ загрузки без краша
- [ ] Savegame roundtrip: save → load → save → load — бивуаки не теряются и не дублируются
